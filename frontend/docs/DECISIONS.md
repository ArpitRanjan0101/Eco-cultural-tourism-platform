# Frontend Decisions — Jharkhand Eco & Cultural Tourism

Decision record for the Next.js frontend and BFF. Backend decisions live in
[../../docs/architecture/DECISIONS.md](../../docs/architecture/DECISIONS.md) and are cited by their own ids
(e.g. backend **A4**, **E7**). Frontend ids use the **W** series (web); open questions use **WO**.

- IDs are permanent. A replaced decision keeps its row with a **Status** note pointing forward.
- Status is *Active* unless marked *Proposed* (awaiting owner approval at a phase gate) or *Superseded*.
- W decisions are **Proposed** until the Phase 0 gate is approved. Gap rows (§3, G series) are **Confirmed**
  facts about the current backend contract.

## 2. Architecture

| ID | Decision |
|----|----------|
| W1 | **Next.js App Router, JavaScript/JSX only**, `jsconfig.json` path alias `@/*` → `src/*`. No TypeScript, Redux, GraphQL or microfrontends. Exact versions pinned in Phase 1 after checking the registry (same rule as backend J5: exact pins, releases at least two weeks old). |
| W2 | **Feature-first modules.** `src/features/<feature>/` owns that feature's API functions, query keys, Zod schemas, hooks and feature components. `src/components/` holds only feature-agnostic, props-driven presentational components. Features may import `components/`, `lib/`, `hooks/`; a feature never imports another feature's internals, only its `index.js` exports. `app/` route files stay thin: load data, compose feature components. |
| W3 | **Two backend access paths, both server-side.** (a) Server Components / route handlers call the **server-only backend client** (`lib/api/`), guarded by the `server-only` package. (b) Browser code calls **BFF route handlers** under `/api/*` on the Next.js origin, which use the same client. The browser never knows the Express URL, the service token or the user's JWT. `login` and `refresh` return tokens in the response body (verified in `openapi.json`), so they are handled only by dedicated BFF auth handlers that move the tokens into cookies and return the user without them. |
| W4 | **Express owns business rules.** The frontend never computes prices, taxes, refunds, availability or permissions it acts on. It displays the backend's decimal strings and states. Client-side Zod validation is UX only and mirrors backend limits; the backend's 422 `details[]` are mapped back onto form fields. |
| W5 | **BFF forwarding is an allowlist generated from the contract.** One catch-all handler (`app/api/v1/[...path]/route.js`) forwards only `(method, path pattern)` pairs present in `docs/api/openapi.json`, excluding `/health/*`, the webhook route and the four session routes. The allowlist is a generated file (`lib/bff/allowlist.generated.js`), regenerated with API_MAPPING.md. Unknown operations get 404 `ROUTE_NOT_FOUND` from the BFF without calling Express. This makes "invent an endpoint" impossible at runtime. |
| W6 | **Session in HttpOnly cookies, refreshed in one place.** Cookies: access token and refresh token, both `HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure` + `__Host-` prefix in production; lifetimes from `accessTokenExpiresAt` / `refreshTokenExpiresAt`. Refresh happens **only** in Next.js request middleware (Server Components cannot set cookies). It refreshes when the access token is missing or expires within 60 s, writes the new cookies on the response **and** overrides the forwarded request cookies so the same request renders with the new token. Backend A4 revokes the whole session family if a rotated refresh token is reused, so refresh is **single-flight per refresh token** in the process (shared promise on `globalThis`, result kept ~30 s for parallel requests that still carry the old token). This holds for one `web` instance (WO7). Failed refresh → cookies cleared, request continues anonymous. |
| W7 | **CSRF on BFF mutations** (backend C12 assigns CSRF to the BFF). Every non-GET `/api/*` request must pass (1) an `Origin` (or `Referer`) check against `APP_ORIGIN` and (2) a double-submit token: a non-HttpOnly `csrf` cookie echoed in an `X-CSRF-Token` header by the shared browser fetch helper. Failures → 403 `CSRF_FAILED`, no backend call. Server Actions are not used for backend mutations, so there is one mutation path to secure and test. |
| W8 | **Forwarded headers.** The BFF sends `X-Internal-Service-Token`, `Authorization: Bearer` (only when a session exists), `X-Request-Id` (generated or propagated, returned to the browser), `X-Client-Ip` (end-user IP; without it backend A7/A8 rate limits and lockouts would apply to every user at once), and passes through only `Idempotency-Key` and `X-Partner-Id` from the browser. Every other inbound header is dropped. In production the client IP is read from the forwarding header set by the trusted edge proxy only; exact handling verified in Phase 3. |
| W9 | **Rendering and caching.** Server Components by default; `'use client'` only for interaction (forms, booking widget, filters, maps, upload). Public catalogue and CMS reads (service token only, no user data) may use time-based revalidation (default 60 s, tuned per page in Phase 4). Anything with a user session, prices in a quote, availability, bookings or payments is `no-store`. A cached listing may show the API's indicative "from" price; the authoritative price is shown only from a live quote. |
| W10 | **TanStack Query** for client-side server state: query keys from per-feature factories (`features/<f>/queryKeys.js`), mutations invalidate by key prefix, retries off for mutations and for 4xx. Server-rendered data seeds queries through `HydrationBoundary` where the page is interactive. |
| W11 | **Forms**: React Hook Form + Zod resolver. One shared mapper turns the backend error envelope into RHF field errors (422 `details[]`) or a form-level message (other codes), always showing `requestId` for 5xx. |
| W12 | **Money and dates.** Money stays a decimal string end-to-end; formatting with `Intl.NumberFormat('en-IN', { style: 'currency', currency })` from the string, never float arithmetic. Calendar dates are `YYYY-MM-DD` strings (backend P6) and are formatted without time-zone shifting; instants are formatted in `Asia/Kolkata`. |
| W13 | **Permissions in the UI are presentation only.** Layouts for `/account`, `/partner`, `/admin` load `GET /auth/me` server-side and redirect anonymous users to `/login?next=…`; missing permissions render a 403 page. Menu items and buttons are hidden by permission code (PERMISSIONS_MATRIX.md). The backend re-checks everything (backend A3, D4). |
| W14 | **Partner context.** With one membership no header is needed (backend C6). The BFF forwards `X-Partner-Id` from an HttpOnly cookie on `/partners/me*` calls when one is set. A selector for several memberships needs a list of the user's organisations, which the contract does not offer (gap G3, WO10); until then `PARTNER_CONTEXT_REQUIRED` / `NOT_A_MEMBER` show an explanatory state. |
| W15 | **CMS rendering** uses an approved section registry (`src/cms/sectionRegistry.js`) mapping the backend's 8 section types (B9) to components, with Zod schemas of the **rendered** shape (CMS_CONTRACTS.md). An unknown type or a section that fails its schema is skipped and logged server-side, never rendered raw. No `dangerouslySetInnerHTML` anywhere in CMS code. |
| W16 | **Media.** Images use the absolute URLs the API returns. Uploads follow backend B2: BFF `upload-init` → browser `PUT` straight to the presigned storage URL → BFF `upload-complete`. The storage origin is configured by env and added to CSP `img-src` / `connect-src` and `next/image` `remotePatterns`. Private documents are opened only through the API's short-lived signed URLs. |
| W17 | **Payments.** Razorpay Checkout script is loaded only on `/checkout/[bookingId]`; CSP allows its origins only there. Order creation and `POST /payments/verify` go through the BFF; the result page shows the backend's `outcome`/statuses only. `503 PAYMENTS_NOT_CONFIGURED` (development default, backend F1) shows a truthful "online payment unavailable" state, never a fake success. |
| W18 | **Email deep links.** Backend emails link to `/verify-email`, `/reset-password`, `/login`, `/forgot-password`, `/partner`, `/partner/bookings/:id` (all exist in the target route map) and `/bookings/:id`. The target structure puts traveller bookings at `/account/bookings/[id]`, so `next.config.mjs` adds a permanent redirect `/bookings/:id` → `/account/bookings/:id`. No backend change. |
| W19 | **Security headers** set by Next.js: CSP with nonces for scripts, `frame-ancestors 'none'`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Content-Type-Options: nosniff`, `Permissions-Policy` minimal. HSTS stays owned by the production nginx edge (backend J3). No secrets in any `NEXT_PUBLIC_*` variable; server env is Zod-validated at startup and the process exits naming missing keys only. |
| W20 | **Design tokens** are defined once (Tailwind theme + CSS custom properties) for colour, type scale, spacing, radius, shadow and motion. Components expose documented `variant` / `size` props; no ad-hoc hex values or one-off spacing in feature code. Every component and its variants are listed in COMPONENT_CATALOG.md. |
| W21 | **Accessibility baseline**: WCAG 2.2 AA — semantic HTML first, visible focus, keyboard-operable widgets, labelled form controls with error association, colour contrast checked in tokens, `prefers-reduced-motion` respected. |
| W22 | **No fake data.** Empty, loading and error states are real UI states. No hardcoded prices, ratings, availability or placeholder content presented as real. Development content comes from the backend's seeds (demo destinations are labelled unverified by the backend, B11). |

## 4. Infrastructure

| ID | Decision |
|----|----------|
| W23 | **Docker only.** `frontend/Dockerfile` (multi-stage `dev` / `prod`, same `node:22.12.0-bookworm-slim` base as the backend, non-root, `output: 'standalone'` for prod, lockfile installed with `npm ci`). A `web` service is added to the root `docker-compose.yml`: dev publishes `127.0.0.1:3000`, joins the `edge` network and reaches the API at `http://nginx:8081` (the private listener). Source is bind-mounted in dev with file-watch polling (Windows/OneDrive host). Production joins the backend's `bff` network (backend J2); serving the site publicly needs a change to `infrastructure/nginx/prod.conf`, planned for Phase 10 and approved separately. The lockfile is generated inside Docker, as for the backend. |
| W25 | (Phase 1, refines W23) The `web` service lives in **`frontend/compose.dev.yml`**, a separate compose project (`jharkhand-tourism-web`) that joins the backend's existing network as external `jharkhand-tourism_edge`. The root `docker-compose.yml` and backend services are unchanged; the backend stack must be up first. Using the backend's project name was rejected: `--remove-orphans` could then delete backend containers. |
| W26 | (Phase 1) **webpack for dev and build** (`next dev --webpack`, `next build --webpack`). Turbopack ignores `WATCHPACK_POLLING`, and bind mounts from the Windows host deliver no file events: verified that edits were never picked up under Turbopack but were within ~2 s under webpack. The build uses the same bundler, so dev and prod do not diverge. Revisit when Turbopack supports polling. |
| W27 | (Phase 1) **Build toolchain:** `node:22.23.2-bookworm-slim` (Node 22.12.0 lacked two years of patches and failed engine ranges of eslint-visitor-keys/jsdom) with **npm pinned to 11.21.0** in the image: npm 10.9.x (including 10.9.8 bundled with Node 22.23.2) crashes building this tree (`edgesOut` of null). Lockfile generation and `npm ci` use the same pinned npm. BuildKit cache mounts keep the npm cache and `.next/cache`; the e2e image installs only `@playwright/test` (equal to the Playwright image tag). The frontend no longer shares the backend's Node pin; that is deliberate and frontend-only. |
| W28 | (Phase 1) **Accepted dev-only audit finding:** `npm audit` reports 5 high findings, all one chain `eslint-config-next → @next/eslint-plugin-next → fast-glob → micromatch → braces` (GHSA-vfj7-8cjw-p6xm, ReDoS-style stack exhaustion from crafted glob patterns). No patched `braces` exists; the suggested fix is eslint-config-next 14 (incompatible with Next 16). The linter only receives globs from our own config, and none of these packages are in the prod image (verified). Re-check on each dependency update. |
| W29 | (Phase 2, corrects Phase 1) **No route-level `loading.jsx` above pages that can call `notFound()`.** A root `app/loading.jsx` wraps every page in Suspense, so the response streams before the page runs and `notFound()` can no longer change the status: verified in production that a gated page served the not-found UI with **HTTP 200** (Phase 4 destination 404s would have been 200 for search engines). The root `loading.jsx` is removed; `PageLoading` is used as a `<Suspense>` fallback around slow page parts instead. After removal the same page returns **404** (verified). |
| W30 | (Phase 2) **Design-system showcase and e2e target.** `/design-system` renders a usage example of every shared component: available in development, 404 in production unless `ENABLE_DESIGN_SYSTEM=true`. Browser tests run against the **production build** (`web-e2e` service, which sets that flag) rather than the dev server: four Chromium workers against the dev bundle crashed or timed out in the Docker Desktop VM, and testing the build users get is more meaningful. Playwright uses 2 workers and a 1 GB `/dev/shm`. |
| W31 | (Phase 2) **No UI component library.** Overlays use the native modal `<dialog>` (inert background, top layer) plus a Tab wrap; menus, tabs, accordion and carousel implement the WAI-ARIA patterns directly; form controls are native elements. Added dependencies are test-only: `@testing-library/user-event` 14.6.7, `axe-core` 4.13.0 (component tests), `@axe-core/playwright` 4.13.0 (e2e image). Colour contrast is checked by `theme.test.js` (21 pairs) and the full-page axe scan in Chromium, since jsdom cannot compute it. |
| W32 | (Phase 3, refines W8) **Client IP from X-Forwarded-For by trusted hops.** Next.js appends the socket peer to `X-Forwarded-For`; with `TRUSTED_PROXY_HOPS=n` the client is the entry `n` from the right (1 = direct, as in development and `web-e2e`; 2 = behind one edge proxy, the production value to set in Phase 10). Invalid values are not sent. Verified: backend rate-limit keys (`rl:auth_login:<ip>`) carried the calling container's IP, not the BFF's or nginx's. |
| W33 | (Phase 3) **`E2E_INSECURE_HTTP` for the browser-test target only.** Real sign-in tests need cookies over plain http inside Docker, which production rules (https origin, Secure `__Host-` cookies) forbid. This flag relaxes only those two startup checks, prints a warning at boot, and is set only on `web-e2e` in `compose.dev.yml`. The placeholder-token check still applies. Must never be set in a deployment. |
| W34 | (Phase 3, refines the Phase 3 folder sketch) **Only session routes get dedicated handlers.** `login`, `logout`, `logout-all`, `refresh` and `/api/session` are in `app/api/auth/*` and `app/api/session` because they read or write tokens. Register, forgot/reset password, verify/resend and change-password carry no tokens and use the generic forwarder at `/api/v1/auth/*`: one mutation path, same CSRF, allowlist and envelope, instead of near-identical per-route handlers. |
| W35 | (Phase 3) **Cleared cookies carry `Max-Age=0` and an epoch `Expires`.** When a server component redirects after the proxy cleared a dead session, Next.js 16 repeats the proxy's cookies without `Max-Age`. With only `Max-Age=0` the browser kept empty session cookies; found by the refresh-reuse e2e test and fixed. |
| W36 | (Phase 3) **Refresh happens in the proxy; `/api/auth/refresh` is the explicit fallback.** The proxy (Next 16 `src/proxy.js`) rotates when the access token is missing or expires within 60 s, then overrides the forwarded request cookies so the same render uses the new token. Rotation is single-flight per refresh token in-process (`globalThis`, shared by proxy and route handlers), results kept 30 s; transient failures are not kept, so they can be retried. 401/422 from `/auth/refresh` clears the session. Server layouts read the current path from an `x-jt-pathname` request header that only the proxy sets (inbound copies are stripped). |
| W37 | (Phase 4, owner-approved) **CMS homepage sections extended in the backend, not hardcoded in the frontend.** The Phase 4 list needed 8 sections the backend registry did not have. The owner chose to extend the backend (B14, migration 0017) so the whole homepage stays admin-controlled; the frontend registry mirrors the backend's 16 types exactly, checked against a generated type list. Live supply cards are resolved by the backend from published supply only. |
| W38 | (Phase 4) **Public chrome is per-request; CMS data is cached.** The public layout is `force-dynamic` (header shows the signed-in user and admin link by permission); CMS reads use the fetch cache (60 s, announcements 30 s, tag `cms`) without per-request headers so the cache key is stable. Menu/announcement/session failures degrade (fallback nav, no bar, signed-out header) instead of an error page; page content failures surface through `error.jsx`. Build-time prerendered files (robots.txt, not-found) never read runtime configuration. |
| W39 | (Phase 4) **CMS e2e uses a real admin and a throwaway landing page.** The suite signs in as an existing admin (credentials passed as `E2E_ADMIN_EMAIL`/`E2E_ADMIN_PASSWORD` at run time, never stored), creates a landing page through the BFF, checks draft privacy via the uncached API, publishes, renders it in Chromium with axe, then archives it — the dev homepage is never overwritten. |
| W40 | (Phase 5) **One map abstraction.** `components/maps`: `MapView` lazy-loads the only Leaflet wrapper (`LeafletMap`, browser-only, CSS loaded with it) via `next/dynamic` (`ssr: false`); `toMapPlaces` turns API cards into places and drops anything without valid API coordinates (never invented or defaulted); markers are CSS `divIcon`s, keyboard-focusable, titled with the place name; popups are built with DOM text nodes (no HTML strings). Every map sits beside an equivalent list (`MapListToggle` defaults to the list; `NearbyMapPanel` shows both). Scroll-wheel zoom only while the map has focus. |
| W41 | (Phase 5) **Discovery data paths.** Listing/detail pages are Server Components reading the API with `getCatalogue` (fetch-cached 60 s, tag `catalogue`, no per-request headers). Search uses `getLive`: never cached, and it forwards the visitor's IP and request id because `/search` is rate-limited per IP (W8, W32). Browser-side calls (autocomplete, near me) go through the existing generic BFF forwarder `/api/v1/*`; the Phase 5 folder sketch's per-resource `app/api/{destinations,districts,search}` routes were not created because they would duplicate the allowlisted forwarder (W5, W34). |
| W42 | (Phase 5) **URL is the filter state.** Every filter, sort, tab and page is a GET form or link; `hrefWith` keeps the other filters and resets the page on filter changes; each page parses its `searchParams` against the contract (`parseDestinationQuery`, `parseSearchQuery`) and silently drops invalid values instead of forwarding them. Only API-supported filters are offered: destination sorts come from `/search/filters`; search has no sort; location/category search filters apply to destinations only, so other result tabs are shown unavailable while filtered; non-destination search paging is capped to the backend's 500-result window. Filtered list pages and search results are `noindex`; the sitemap lists main sections, districts and published destinations. |
| W43 | (Phase 5, extends W33) **Geolocation in e2e.** Browsers expose geolocation only on secure origins (https or localhost); the e2e target is http inside Docker and Chromium's headless shell ignores `--unsafely-treat-insecure-origin-as-secure` (verified: `isSecureContext` false). The near-me e2e therefore stubs only `navigator.geolocation` with a fixed position; the click, BFF request, `/search/nearby` response, cards and map are real. Refusal/unavailability is covered by unit tests. Production is https. "Near me" never guesses a location: it asks for the device position only on click and explains refusal or failure. |
| W44 | (Phase 5b) **One supply layer, four owners.** Stays, guides, experiences and packages share presentational building blocks in `features/supply` (`SupplyListing`, `SupplyFilters`, `SupplyResults`, `SupplyHero`, `AtAGlance`, `BookingModeBadge`, `SeatList`, `LiveAvailability`/`AvailabilityResult`, `useAvailability`) and generic helpers (`lib/url/listQuery` `parseListQuery`, `lib/bff/catalogue` `catalogueList`/`catalogueItem`/`catalogueOptions`, `components/data-display` `AboutSection`/`GallerySection`/`PlainText`, `filterChips`, `plural`). Each operation keeps exactly one owning feature (LLD §1): `properties`, `guides`, `experiences`, `packages` own their schemas, server fetchers, browser services and detail sections; `reviews` owns `GET /reviews` (`getReviews`, `ReviewsSection`). Phase 5 code with the same logic (destination query parsing, chips, filter options via `geography.adapter`, overview/gallery/reviews sections, booking badge, plurals) was moved onto these helpers so nothing is implemented twice. |
| W45 | (Phase 5b) **Live availability is a browser island; everything else is cached.** List and detail pages are Server Components on `getCatalogue` (60 s, W41). Availability (`/properties/:id/availability`, `/guides/:id/availability`, `/experiences/:id/availability`, `/packages/:id/availability`) is read in the browser through the allowlisted forwarder (no new BFF route, W5), so it is never cached, carries the visitor's IP for the backend's per-IP limits (W8) and runs on load with sensible defaults (stay: tomorrow → day after, 2 adults, 1 room; guide: the backend's 14-day window; experience: 30 days from today for the minimum party; package: the minimum party). Forms mirror the backend limits (stay 1–30 nights from today; guide window ≤ 92 days; party sizes within the item's own min/max) and show the backend's 422 detail, 404 and 429 `Retry-After` as plain text. The UI shows only API figures: room totals (`totalPrice` = nights × rooms), per-room nightly prices, per-person session/departure prices, per-group guide prices; it never multiplies a price or derives seats (W4). Separate reads that the detail DTO already carries are not made (`/properties/:id/rooms`, `/guides/:id/services`, `/experiences/:id/sessions`, `/packages/:id/departures`); `GET /amenities` is not used because `GET /properties` has no amenity filter. |
| W46 | (Phase 5b) **Catalogue links stay truthful.** Destination pages link on to `/experiences?destination=` and `/guides?destination=` with the section's own total (same backend filter). Their stays section also includes stays within 25 km, which `/properties?destination=` does not, so it links to the district's stays without a count. `destination` is a URL-only filter on the list pages (kept by the filter form, removable as a chip). |
| W47 | (Phase 5b, extends W39) **Supply e2e creates its own data.** `supply.spec.js` builds real supply the way the product does — a new partner registers (real Mailpit email), applies as `multi`, the admin approves it; the partner lists a stay, guide, experience and package; the admin publishes/verifies them — then suspends all of it (and the partner) in `afterAll`. A separate partner account is required because admins cannot verify a guide of their own organisation (backend `SELF_REVIEW_FORBIDDEN`). Names carry a per-run stamp so list queries never hit a 60 s-cached page. Supply reviews need a completed (paid) booking, so the browser suite checks the real "No reviews yet" state and rendered reviews are covered by unit tests. Each run registers one more account (backend limit 10/hour per IP, shared with `auth.spec.js`). |

Phase 3 (moved from Phase 1, where nothing consumes the allowlist yet) replaces it with a Node script run in Docker that emits both API_MAPPING.md and the BFF allowlist (W5), so the two cannot drift. **Done (Phase 3):** `scripts/generate-contract.mjs` (`npm run contract:generate`, contract mounted read-only at `/contract`); its 242 mapping rows are identical to the PowerShell output, which was then deleted; 234 operations forwardable. |
